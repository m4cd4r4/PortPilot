# Follow-ups

Captured, not built. Each came up while building something else.

- **Share one run filter.** `filterRuns` in `src/core/runView.js` mirrors `findRuns` in `mcp-server/index.js`. They must stay in step by hand; move both onto one shared module when the MCP server can import from `src/core` (found in PR B2, run-history-view).
- **Loopback probing.** `healthCheck.probe` and thumbnail capture use `127.0.0.1` only; a server bound to `::1` (Vite on recent Node on Windows is the likely case) would never show as live or get a thumbnail. Confirm with a default Vite app, then probe `localhost` too.
- **Port rewrite limits.** A `-p`/`--port` hidden inside a package.json script, or two different `--port` flags in one command (`concurrently`), is not rewritten; the PORT env var is all Re-run sets. Consider probing the new port after start and warning when nothing answers there.
- **History view cost.** The 4 s poll sends the whole runs array over IPC and parses `runs.json` two or three times per call; `load()` has no in-flight guard, `h.thumbs` never evicts, and rewriting the list's `innerHTML` on each progress event can drop focus. Diff the rows, or send only changes.
- **Thumbnail frames.** The capture window guards the main frame only (`will-navigate`, `will-redirect`); add `will-frame-navigate` if the page's iframes ever matter. The window is sandboxed with no preload and a separate partition.
- **MCP `rerunSteps` lacks the yarn-berry `--immutable` branch** the desktop install uses (`mcp-server/index.js`, `src/core/rerun.js`).
- **Stop leaves the server running on Linux.** `processManager.killProcess` runs `kill -9 <pid>` on the shell wrapper only, so the node child can keep its port after Stop (Windows uses `taskkill /T`). Found when CI's Re-run test hit EADDRINUSE on ubuntu. Kill the process group.
- **History in the VS Code view** is plan row #22.
- **Re-run clean-up.** Deleting a re-run app does not run `git worktree remove` for its sibling worktree yet (found in PR B2).
- **Live preview per app (row previews follow-up).** The Apps row shows the run's one-off thumbnail, taken when the page first answers, so it can go stale while the app keeps running. A refreshing preview per app is a separate, larger idea (capture cadence, cost, privacy); the row drawer has no preview either. Plan row #23 covers the static row thumbnail only.
- **VS Code row preview follow-ups (plan row #25).** The preview is a hover card only: a tree icon is a fixed ~16 px box that would replace the state glyph, so an inline thumbnail is not possible. An optional 16 px icon variant could be a setting. `portpilot.rowPreviews` is independent of the desktop `settings.rowPreviews`; honouring the desktop setting from the extension is a separate decision. The extension reads thumbnails as data URIs capped at 512 KB; the desktop writes ~480 px JPEGs, well under that.
- **Browser profiles follow-ups (plan row 26, slice 1).** (1) The config restore/import in `src/main/configStore.js` rebuilds the config from known keys, so check it keeps `browserProfiles` (the user-data-dirs live beside the config and are untouched either way). (2) Launcher extras not ported from the personal pool: the labelled window title (patching `Preferences` `profile.name` while the browser is down) and the identity start page. (3) Offscreen placement is verified on Windows only: macOS keeps a window on a screen and Wayland ignores positions, so the start result reports `offscreen.parked` honestly; decide whether to fall back to headless there. (4) Port holder lookup shells out (`netstat` + PowerShell on Windows, `lsof`/`ss` + `ps` elsewhere), about 300 ms on Windows per held port; slice 2's poll should cache it. (5) No CDP-less stop for a browser PortPilot did not start (`owner: 'unverified'` is refused on purpose). (6) Claim/lease so two sessions cannot drive one profile stays open, as in the plan row.
- **Browser profiles follow-ups (plan row 26, slice 2a: surfaces).** (1) Claims are advisory by design and live in `portpilot-browser-claims.json` beside the config; a claim is shown only while the pid it was made for is the one running, but `removeProfile` does not delete its claim entry, and nothing prunes old entries. (2) The web agent does not broadcast browser start/stop over SSE, so a future desktop panel must poll or the route must emit `config-changed`-style events. (3) `start_browser` has no per-start `mode` override; use `set_browser_mode` then restart. (4) `scripts/browser-profiles.js` still calls the core directly; it could call `browserApi.call` so the CLI, MCP and HTTP share error wording. (5) `browserApi.cjs` is a bundle with its own copy of `configFile`; locks are on disk so this is safe, but its lazy run-history hook finds no `runHistory` and skips quietly. (6) `list_browser_profiles` re-reads the port holder per profile (about 300 ms each on Windows when held): the slice 1 cached-lookup follow-up now matters for a model that polls.
- **Browser surfaces review leftovers (plan row 26, slice 2a).** From the Opus review, not fixed in the PR: (1) the VS Code runtime list (`vscode-extension/scripts/copy-runtime.js`) was already missing `main/healthCheck.js`, `main/shareInfo.js`, `main/portReserver.js` and the npm `qrcode` dependency that `core/dispatch.js` needs, so the portal likely cannot start from the .vsix; this PR adds only the browser modules. Add a test that loads `agent/server.js` from the copied runtime. (2) A claim with `pid: null` (owner could not be identified) sticks to any later browser on that profile. (3) `configFile.readJson` copies a corrupt claims file to `.corrupt-<ts>` on every read; a polling client makes unlimited copies. (4) Slice 1's `NOT_VERIFIED` start message says "pick another port", which contradicts the surfaces' rule. (5) Raw Node error codes (EPERM, ENOENT) pass through as API codes with absolute paths in the message; map them to `INTERNAL` and strip paths. (6) CDP tab titles and URLs reach the model uncapped; cap length. (7) No per-profile serialisation: two simultaneous `start_browser` calls can both spawn (Chromium hands the second to the first). (8) `plugin/hooks/register.test.ts` runs only locally via `claude plugin test plugin`, and `stop_browser` stamping is untested.
- **Browser profiles follow-ups (plan row 26, slice 2b: Browsers tab).** (1) Duplicate copies an allowlist (`Default/Preferences`, `Default/Secure Preferences`, `Default/Extensions`) and writes only the `extensions` and `protection` keys of the two preferences files, because they also hold `account_info`, visited-site engagement scores and the Brave wallet. So Duplicate carries extensions only, not other browser settings (narrower than the "settings + extensions" option chosen on 2026-10-10). Verified: no credential file and none of those keys reach the copy. NOT verified: that Brave or Chrome accept the filtered `Secure Preferences` as the same installed extension (its integrity MACs are machine- and user-bound, and the filter may drop MAC entries the browser expects), because a real Web Store install was never copied end to end. Test it by hand with a real password manager before telling anyone Duplicate carries extensions over. (2) The panel polls every 4 s through a 1.5 s cached, single-flight `browser:list`; the per-held-profile holder lookup (about 300 ms on Windows) is still uncached, so ten held profiles make a slow poll. (3) Remove keeps the folder (and its sign-ins) on disk; there is no "delete the folder" action in the UI, only `removeProfile(..., { purge: true })` in the core. (4) The panel has no import-from-`pool.json` action; that is still the CLI's `--import-pool`. (5) The config watcher now ignores `browserProfiles` when deciding to announce a config change, so a profile edit no longer toasts "Apps list updated"; if a future surface needs a live profile list pushed to it, give it its own channel. (6) `tests/config-atomic.test.cjs` "two concurrent writer processes" fails about one run in two on a loaded machine (lock timeout); it passes on retry and the cause is not looked at. (7) There is no `tests/*.e2e.js` for the Browsers tab; the real-Electron check was a throwaway CDP script, so a repeat needs rewriting. Worth porting `tests/history-ui.e2e.js` to cover Start, Stop, Duplicate. (8) NOT fixed from the Opus review: one malformed stored profile (for example `{ "name": "old one" }`, hand-edited into the config) makes `browserRun.allStatus` throw, so the whole tab shows "Could not read the browser profiles", and the UI Remove also fails with `BAD_NAME` because it validates the stored name. Fix: a per-row catch in `allStatus` that returns a broken-profile row, and a remove-by-raw-name path.
